## [2026-08-07 | 启动必现"目标凭据已存在且内容不同"误报：P/Invoke CharSet 根因]
- **Events**：用户报每次启动弹"模型连接的目标凭据已存在且内容不同，未修改配置"。静态排查矛盾：providers.json 引用 `myovo-key`（存在），但目标凭据 `provider/model/myovo/api-key` 用独立 CredRead 探测为 NOT_FOUND——不可能触发 target-conflict。用引用真实 FileJsonStore+WindowsCredentialStore 的临时控制台复现：**迁移器确实抛 target-conflict**；全量枚举凭据发现两条乱码名凭据（`敄歳潴偰瑥...`），其 target 名 UTF-16LE hex 正是 `DesktopPet/provider/model/myovo` 的**紧凑 ASCII**，写入时间恰为每次启动时刻。
- **Changes**：根因 = `CredNative.Credential` 结构体 `[StructLayout(Sequential)]` 缺 `CharSet.Unicode`，string 字段按 ANSI 编组：`CredWrite` 把 target 名以 ANSI 字节交给系统，系统按 CREDENTIALW(UTF-16) 解释成乱码；随后 `CredRead(好名字)` 永远 NOT_FOUND → 迁移器 `Set` 后读回 null ≠ 源 → 误判 target-conflict，**每次启动报错并累积一条垃圾凭据**。修复：加 `CharSet = CharSet.Unicode`；清理 2 条垃圾凭据；迁移器重新执行成功（providers.json 已指向新引用、旧 `myovo-key` 自动删除、凭据内容无损验证）；新增 `WindowsCredentialStoreTests.SetGetDelete_RoundTrip_PreservesTargetNameExactly` 真实凭据 round-trip 回归测试（Infra.Tests 104 全过）。
- **Insights**：① P/Invoke 结构体含 string 字段必须显式 CharSet.Unicode，缺省按 ANSI 编组是静默损坏——单测（InMemory 假凭据）覆盖不到，必须真实 Credential Manager round-trip；② 迁移器把"Set 后读回不一致"统一映射为 target-conflict 会掩盖写入损坏类故障，故障分类应区分"目标已存在且不同"与"写入后读回异常"；③ 垃圾凭据名不匹配 `DesktopPet/*` 过滤器（系统视角名字已是乱码），`DeleteAll` 清理不到，只能全量枚举按 UTF-16 hex 特征识别；④ 诊断优先用真实代码路径复现（临时 console 引用 Infra），不要停留在静态推演。

## [2026-08-14 | 退出挂死 + 托盘图标残留：三层 dispose 缺陷链（VS MCP + SOS 取证）]
- **Events**：用户报「点了退出但托盘图标还在」。VS MCP build 报 MSB3021（exe 被锁）→ 发现 DesktopPet.App (PID 21312) 存活 35 分钟、Responding=True、WS 370MB、112 线程。附件调试器：主线程卡 `App.OnExit` App.xaml.cs:545 的 `_ai.DisposeAsync().GetAwaiter().GetResult()`；`dotnet-dump` 两次 dumpasync 均显示 `DisposeCoreAsync`(state=2) → `AsyncGenerationOwner.DisposeAsync` 挂起；SOS 逐层 dumpobj 取证：AsyncGenerationOwner `_disposed=1/_current=null`，HashSet `_count=1`（1 个 entry 未被移除），entry `LeaseCount=0/Retired=1/DisposeStarted=1`，Disposed TCS Task 未完成 → `DisposeEntryAsync` 卡在 `entry.Value.DisposeAsync()`；Scheduler `DisposeCoreAsync`(d__33) 与 AsyncGenerationOwner(d__9) 的 Task 标志位均非完成态（对照 Task.CompletedTask=0x01004000）。恢复进程 35s 后仍卡同一行 → 永久挂起确认。
- **Changes**：三层修复（设计缺陷，非方法误用）——① `ModelRequestScheduler.DisposeCoreAsync`：`await loop` 改 `Task.WhenAny(loop, Task.Delay(5s))`（worker 卡 provider 网络调用时不再无限等）；② `AsyncGenerationOwner.DisposeAsync(timeout)`：超时后不再 `await Task.WhenAll(pending.Concat(...))`——pending 含已卡死 entry（DisposeStarted=true）时 WhenAll 永久挂起、兜底形同虚设；改为只对未启动 entry 强制释放并再等 5s 短窗口后放弃；③ `App.OnExit`：`_ai.DisposeAsync()` 加 10s 总超时（`Wait(TimeSpan)` 超时返回 false 继续清理，托盘 Dispose 必执行）。验证：VS build 0 error；768 测试全绿（Core 500/Infra 172/Agent 38/App 58）；真机复现——keybd_event 模拟 Win+Ctrl+X（SendKeys 的 `^#x` 在本机不触发全局热键，是测试工具坑非 App bug），退出 0.3s 完成（修复前永久挂起）。
- **Insights**：① 「退出后托盘图标还在」≈「进程没死」：先查 `Get-Process` 再查代码；exe 被锁（MSB3021）是进程存活的最快信号；② 退出链路任何一层 `await` 无超时 + 外层同步 `GetAwaiter().GetResult()` = 永久冻结三要素；超时兜底必须「超时后不再等原任务」，否则只是换了等待对象；③ dotnet-dump + SOS（dumpasync/dumpobj/dumpheap）是断点堆栈之外的 async 挂死取证利器：状态机 `<>1__state` 定位 await 序号，`<>u__N` awaiter 链可追到具体 ValueTask 对象；HashSet `_count` vs `_freeCount` 区分活动/已删槽位；④ `-type` 是子串匹配，泛型类型会匹配出一堆相关对象，精确类型要带完整命名空间再人工筛选；⑤ 退出路径测试：keybd_event 直发 Win+Ctrl+X 比 SendKeys 可靠；修复后应计时退出（<10s 为正常）。
