# 确认缺口

1. **高：运行时从 0 秒重新启用轮换无效。**  
   当 renderer 在设置值为 0 时加载，`PetWindow.LoadSpriteAsync` 传入的 playlist 为 `null`，见 `PetWindow.cs:525-532`。随后把设置改成大于 0，只会调用 `PetRenderer.SetIdleIntervalMs`；该方法在 `_idle is null` 时直接返回，见 `PetRenderer.cs:48-53`。  
   结果：UI 显示已启用并持久化，但当前窗口直到重建/重启仍不会轮换。

2. **中：运行时把轮换设为 0，不保证立即回到第一个动作。**  
   `PetWindow.ApplySettings` 只更新 interval，见 `PetWindow.cs:312-318`；`AdvanceFrame` 在值为 0 后停止切换，但不会清除 `_idleRow` 或重置为 clip 0，见 `PetWindow.cs:700-710`。  
   若关闭前停在其他行，窗口会继续播放该行，违反设置页“0 = 关闭，只播第一个动作”的说明（`SettingsWindow.cs:642-645`）。

3. **高：130% 尺寸在成长叠加路径可能越界写帧缓冲。**  
   工作区把 `_sizePercent` 乘到 fit 上，允许 `SpriteRect` 超出缓冲；新增测试甚至明确期望 320×360 精灵绘制到 260×320 缓冲并产生负 Y，见 `PetRendererTests.cs:215-226`。  
   但 `PetRenderer.DrawFrame` 在 `PetRenderer.cs:183-202` 写 buffer 时没有对 `x/y` 做边界裁剪。普通无成长叠加路径通过 WPF `Image` 缓存呈现，不写 buffer；有 `GlowColor` 时 `PetWindow.TryPresentCachedSpriteFrame` 返回 false，转入 `DrawFrame`，见 `PetWindow.cs:751-788`，可能触发 `IndexOutOfRangeException`。现有测试只调用 `PrepareFrame`，未覆盖实际 rasterize。

4. **中：设置文案“每个动作都展示”与随机实现不一致。**  
   `PetWindow` 使用 `Random: true`，见 `PetWindow.cs:526-530`；`PetRenderer.AdvanceIdleClip` 每次独立 `Random.Shared.Next`，允许连续命中相同行，也不保证一轮覆盖所有行，见 `PetRenderer.cs:97-105`。  
   因而“多个动作随机抽取”真实，“每个动作都展示”不受保证。

5. **中：缺少 App/WPF 层动作集成测试。**  
   当前新增 Core 测试验证了设置钳制、尺寸、bob 和原有静态 playlist，但没有验证：
   - 0 → 非 0 能即时创建/启用 playlist；
   - 非 0 → 0 回到第一行；
   - 设置页 `Save` 到当前窗口的完整链路；
   - 窗口计时达到间隔后切行动作；
   - 设置页预览与主窗口动作策略一致。

6. **低：预览与实际桌宠行为不一致。**  
   `PetPreviewCard` 不构造 playlist，见 `SettingsWindow.cs:1733-1739`；若目标包含“设置页实时预览当前动作策略”，该缺口真实。若预览只要求展示素材 row 0，则不属于阻塞项。

7. **低：`SpriteLoader` 的线程安全修改没有消除重复并发加载。**  
   `TryGetCached` 与后续磁盘读取/下载之间没有 per-slug in-flight task 去重，见 `SpriteLoader.cs:55-91`。多个窗口同时首次加载同一 slug 仍可重复读取、解码或下载。它不是动作播放正确性的最小阻塞点，但“共享缓存同 slug 只解码一次”的强假设并不成立。

# 可能重复或错误假设

1. **“需要从 Core 新增动作播放状态机”是重复建设。**  
   HEAD 已有 `IdlePlaylistOptions`、行优先级、开始/停止/推进和相应测试。最小修复应扩展现有 playlist 配置更新能力，而不是再建第二套 action player。

2. **“SpriteLoader 应决定播放哪些动作”边界错误。**  
   `SpriteLoader` 只应负责 bytes → `SpriteSheet` 与缓存。动作选择/播放顺序属于 Core renderer 或独立 playlist policy；时间调度属于 App/window。

3. **“所有切片行天然都是待机动作”不一定成立。**  
   `StateMapping` 明确把标准行解释为 idle、左右跑、挥手、跳跃、失败、等待、工作、review，见 `DesktopPet.Core/Pets/StateMapping.cs:3-28`。工作区无条件把全部 `sheet.Clips` 纳入 idle playlist，可能导致宠物待机时随机播放移动或失败状态。  
   若用户需求确实是“导入素材的每一行都轮播”，当前实现符合该特定产品决定；若需求是“只轮播 idle action 集”，仍缺少可配置 clip 集或素材元数据。

4. **`IdlePlaylistOptions.IntervalMs` 当前不是实际计时来源。**  
   真正的间隔判断使用 `PetWindow._idleActionIntervalSeconds`，见 `PetWindow.cs:700-707`；renderer 内 `_idle.IntervalMs` 除更新外没有被读取。因而 `SetIdleIntervalMs` 目前基本是第二份无效状态。应避免让 interval 同时存在于窗口字段和 renderer options。

5. **“设置即时生效已经完整完成”不成立。**  
   尺寸和 bob 可以即时更新，但 playlist 的存在与 clip 集只在 renderer 构造时决定；interval setter 无法完成开/关切换。

# 建议文件边界

1. **首选最小核心边界：`DesktopPet.Core/Rendering/PetRenderer.cs`**  
   在现有 playlist 模型上提供一个明确的运行时配置入口，例如更新完整 `IdlePlaylistOptions?`，并统一处理：
   - null/空列表：清除 `_idleRow`，回 row 0；
   - 从 null 启用：创建 playlist 并立即 `StartIdleCycling`；
   - clip 列表变化：校验并重置索引；
   - 顺序还是随机的产品语义。  
   不建议只继续扩充 `SetIdleIntervalMs`，因为 interval 并不是 renderer 的计时来源。

2. **App 集成边界：`DesktopPet.App/Windows/PetWindow.cs`**  
   抽出单一 `ApplyIdlePlaylistSettings`，由精灵加载完成和 `ApplySettings` 两处复用。这里保留时钟和 `_lastIdleSwitchMs`，但不要再让 renderer 保存一份未使用的 interval。  
   同文件还需决定 0 时是否立即切回 clip 0。

3. **设置契约边界：`DesktopPet.Core/Storage/AppSettings.cs`**  
   当前字段和钳制足够；若最终需要选择“哪些行”或顺序/随机模式，才在这里新增 clip IDs/mode。仅修当前即时开关问题无需继续扩 schema。

4. **UI 边界：`DesktopPet.App/Settings/SettingsWindow.cs`**  
   保留 slider 和 `Save` 即可。若采取随机模式，应把“每个动作都展示”改为准确描述；若必须保证全覆盖，则让 Core 使用 shuffle-bag 或顺序轮换，而非只改文案。

5. **加载边界：`DesktopPet.App/Rendering/SpriteLoader.cs`**  
   动作修复无需再改此文件。只有要解决并发重复解码时，才单独引入 per-slug in-flight task cache。

6. **像素安全边界：`DesktopPet.Core/Rendering/PetRenderer.cs`**  
   `DrawFrame` 必须裁剪目标坐标，或尺寸语义改成不允许超出固定 buffer。这个问题与动作轮播不是同一需求，但属于当前相关未提交渲染改动的高风险回归。
